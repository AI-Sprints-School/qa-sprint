# Шаблон репозитория QA-спринта

Это заготовка, в которой вы сдаёте работы спринта: десять папок `lesson01`–`lesson10`. Сделайте
её форк, и дальше вся работа идёт в вашей копии.

Ставить на компьютер ничего не нужно: файлы правятся в веб-редакторе
GitHub, тесты запускает GitHub на своей машине, результат виден
во вкладке **Actions** вашего форка и во вкладке **Checks** каждого
pull request.

## С чего начать

1. **Fork** справа вверху, затем **Create fork**.
2. В своём форке откройте вкладку **Actions** и подтвердите запуск
   автоматических проверок зелёной кнопкой. На форках GitHub выключает
   их по умолчанию; делается это один раз на весь спринт. Без этого шага
   не заработают прогоны заданий 3.4, 4.2 и 4.4.
3. Дальше работайте по заданиям на платформе.

## Как сдаётся работа

Одно задание — одна ветка — один pull request **в `main` вашего же
форка**, не в репозиторий школы. Ветки называются по папке: `lesson01`,
`lesson02` и так далее. Номер в имени папки — позиционный, он не равен
номеру главы; соответствие — в таблице ниже. Ссылка на pull request
отправляется в задании на платформе.

При создании pull request GitHub по умолчанию подставляет базой
репозиторий школы. Переключите **base repository** на свой форк,
**base** — `main`, **compare** — ветку задания.

Когда работу приняли, влейте pull request в `main` кнопкой **Merge pull
request**. В задании 4.4 мутационный прогон меряет тесты, которые лежат
в `main`, а в задании 5.2 портфолио собирается из него же.

**Имена файлов заданы за вас** и являются частью критерия приёмки:
проверяющий ищет файл по точному пути. Копируйте имя из задания,
а не придумывайте своё.

## Автоматические прогоны

| Workflow | Когда запускается | Что делает |
|---|---|---|
| `tests` | на каждый коммит и на каждый pull request | прогоняет pytest по папке `lesson08` |
| `mutation` | на каждый коммит в ветку `lesson09`, а также кнопкой | мутационный прогон `mutmut` по `lesson08/wallet_utils.py`, печатает список неубитых мутантов и строку `mutation score` |
| `review-tests` | только кнопкой **Run workflow** | не оценивается; задание 3.4 предлагает запустить её после сдачи, чтобы сверить свою матрицу с машиной (файл `lesson07/wallet_broken.py`, который она подставляет, не удаляйте и не правьте): подставляет заведомо сломанный `lesson07/wallet_broken.py` и прогоняет по нему шесть тестов ревью |

Версии зафиксированы в `requirements.txt` и одинаковы у всей когорты:
Python 3.14, `pytest==9.1.1`, `mutmut==3.7.0`.

Красный прогон — не всегда авария. В задании 4.2 красный прогон до починки
модуля обязателен: он доказывает, что ваши тесты видят баг. В прогоне
`review-tests` часть тестов обязана падать по построению.

## Перед первым запуском коллекции задания 2.4

В стартовой коллекции `lesson05/wallet-collection.json` адрес запроса
записан переменной. Заведите в Hoppscotch окружение и добавьте в него
три переменные, а само окружение выберите активным:

- `base_url` — адрес «Кошелька» из задания на платформе, без
  завершающего слэша;
- `token` — значение, которое вернул вход (`POST /api/auth/login`);
- `password` — ваш пароль от «Кошелька»: в теле запроса входа он
  записан как `<<password>>`, чтобы не попасть в файл коллекции.

Файл окружения в репозиторий не кладётся: в нём лежит ваш живой токен.
В задании 2.4 вы допишете для этого строку в `.gitignore`.

## Переменные окружения для API-тестов задания 4.4

Тесты в `lesson09/` берут доступы из переменных окружения
`WALLET_BASE_URL`, `WALLET_LOGIN`, `WALLET_PASSWORD`. На машине GitHub
их нет, поэтому в прогоне эти тесты честно печатаются пропущенными —
это штатно и на приёмку не влияет. Логины, пароли и токены в коде
тестов не пишутся никогда.
